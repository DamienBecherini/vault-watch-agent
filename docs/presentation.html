Vault Watch Agent

Un agent qui maintient à jour un guide technique de 132 pages sur l'IA auto-hébergée. Il lit la veille de l'écosystème, propose des corrections sourcées, attend une relecture humaine, puis ouvre une pull request.

132pages en français, autant en miroir anglais
408 ktokens de contenu français (mesure exacte)
81 → 8éléments de veille → corrections proposées (issue #50)
0,90 $coût du premier passage réel, 18 appels
Le problème

Un guide technique périme vite

Le guide Zero to Hero : On-Premise AI donne des versions minimales, des prix de matériel, des failles de sécurité à surveiller. Ces faits changent chaque semaine. Une version recommandée qui a une faille critique devient un mauvais conseil.

Le système répartit le travail en trois couches : des scripts sans IA collectent et filtrent, le modèle juge et rédige, l'humain valide. Chaque couche ne fait que ce qu'elle fait de façon fiable.

Déterministe · GitHub Actions

Collecter et filtrer

  • Flux : versions GitHub, avis de sécurité, Hugging Face, constructeurs
  • Pré-tri par règles : pré-versions, correctifs mineurs, avis déjà couverts par les versions plancher du guide
  • Une issue « veille » tous les 15 jours, « urgente » si un avis critique n'est pas couvert
Modèle · Claude Opus 5.5

Juger et rédiger

  • Tri : à corriger, à ajouter, à écarter, avec une raison pour chaque élément
  • Proposition : phrase actuelle citée mot pour mot, phrase proposée datée, source, gravité
  • Sorties structurées validées par schéma, jamais de texte libre à interpréter
Humain + CI

Valider

  • Relecture du rapport, choix des corrections
  • Audits du guide sur la branche : liens, schémas, traductions, métadonnées
  • Feu vert explicite avant push et pull request, fusion manuelle

Analyse

Trois questions sur la tenue dans le temps

Non

Le guide a-t-il un système pour garder une taille raisonnable ?

Non. Les seules règles d'archivage portent sur les fichiers de travail des agents (backlog du lexique). Le contenu lui-même ne fait que grossir, et les rapports de maintenance restent dans le dépôt (un seul rapport fait 460 Ko).

La cause est structurelle : la règle « formulation datée » fait que chaque correction ajoute une précision sans retirer l'ancienne. La correction C1 de ce passage en est un exemple : elle garde l'ancien plancher LiteLLM et en ajoute quatre nouveaux.

Non

Y a-t-il un RAG ?

Non. L'agent cherche les pages par mots-clés, comme le faisait la session Claude Code avec grep. Le guide explique le RAG mais ne l'utilise pas. Les limites se voient dans ce passage : les extraits sont des paragraphes isolés, et une même faille Jan n'a été reportée que sur une des pages qui en parlent.

Oui

Le contenu tient-il dans 1 million de tokens ?

Oui, largement pour le français : 408 k tokens, mesurés avec l'API de comptage. Avec l'anglais, 761 k, ce qui tient encore mais laisse peu de marge.

Recommandations

Ce que je propose de changer

  1. Tout le guide en contexte, avec cache, plutôt qu'un RAG. À 408 k tokens, un appel qui lit tout le français coûte environ 2 $ la première fois, puis environ 0,08 $ par appel tant que le cache est chaud. Le modèle voit alors toutes les pages concernées, les notes de bas de page et les incohérences entre pages. Un passage complet reviendrait à 3 ou 4 $ au lieu de 0,90 $. Un RAG vectoriel n'apporte rien à cette taille ; il deviendra utile si le guide dépasse le budget de contexte.
  2. Mesurer avant de choisir. Les issues #26, #30 et #47 ont déjà été traitées et fusionnées. Elles servent de vérité de terrain : on rejoue l'agent dessus, avec recherche par mots-clés puis avec tout le guide en contexte, et on compare précision et rappel aux corrections réellement fusionnées.
  3. Remplacer au lieu d'empiler. Une page décrit l'état actuel. Une correction remplace l'ancien fait ; l'historique reste dans Git et dans la note de source. La consigne du modèle doit le dire explicitement.
  4. Un budget de taille par page, vérifié en CI. Par exemple 20 Ko pour une fiche, 35 Ko pour une page de référence, en avertissement d'abord.
  5. Une passe trimestrielle de compaction. Un second graphe propose des versions plus courtes des sections qui dépassent leur budget, et retire les avis de sécurité corrigés depuis plus de six mois sous la version plancher. Même règle : diff relu par un humain.
  6. Synchroniser le miroir anglais dans le graphe. Un nœud de traduction (Claude Sonnet 5.5) avant les audits, puisque l'audit i18n-strict bloque sinon.
  7. Vérifier sur le web quand les notes manquent. vLLM 0.33 et les poids de Mistral Large 4 n'avaient aucune note en cache. Un outil de lecture web limité aux sources de rang A permettrait aussi de revérifier les 12 affirmations dues.
  8. Grouper les corrections liées. C2 (note de bas de page) n'a de sens qu'avec C1 : la relecture doit accepter ou refuser un groupe.
  9. Une seule source de consignes. Le skill Claude Code vault-watch et l'agent font le même travail. L'agent devrait charger le contrat brief.md du guide au lieu d'en garder une copie condensée qui finira par diverger.
