vault-watch-agent : structure du code

Un guide de lecture pour développeurs : les modules, l'état du graphe, où le modèle est appelé, et comment un passage en pause survit.

English · Français · Présentation · README

Environ 3 000 lignes de Python dans src/vault_watch_agent/, une page statique sans étape de build, et des tests qui font tourner tout le graphe avec un faux modèle sur un dépôt git jetable. Commencez par graph.py : tout le reste l'alimente ou le pilote.

Les modules et leurs dépendances

Deux règles donnent sa forme à ce graphe :

  • Une seule porte vers le modèle. Seul llm.py importe anthropic. Tous les autres modules reçoivent un objet doté d'une méthode parse(system, prompt, schema, effort, node, context, web) (le protocole LLM) : les tests le remplacent par un faux.
  • Une seule porte vers le guide. Lire, chercher et modifier les pages passe par vault.py ; les appels à git, gh et aux scripts du guide passent par inputs.py. Le modèle ne touche jamais un fichier.

Le graphe, étape par étape

build(deps, checkpointer) reçoit une dataclass Deps : le chemin du guide, le modèle des étapes de raisonnement (llm), celui du miroir anglais (translator), l'activation de la relecture croisée, le dépôt GitHub et sa branche de base, la date du jour. Les étapes sont des fonctions imbriquées qui capturent deps : un test construit le même graphe avec des faux.

L'état qui le traverse

WatchState (state.py) est un TypedDict de valeurs JSON simples : un passage en pause est sérialisé tel quel par le checkpointer. Chaque étape ne renvoie que les clés qu'elle change.

⊕ marque les deux clés qui ont un reducer (Annotated[list, operator.add]) : les branches propose parallèles ajoutent leurs propositions et leur consommation de tokens au lieu de s'écraser. Les classes Pydantic sont l'output_format des appels au modèle : une réponse qui ne valide pas est une erreur, pas une supposition.

Un appel au modèle, de bout en bout

Comment un passage se met en pause et reprend

La ligne de commande et la page web partagent le même fichier SQLite et les mêmes identifiants de passage : un passage lancé depuis l'une peut être terminé depuis l'autre. Le serveur web fait tourner le graphe dans un thread de fond et envoie graph.stream(stream_mode="updates") à la page en server-sent events.

Les passes de correction entrent au milieu du graphe

Une passe de correction fait ses propres propositions, puis indique à LangGraph qu'elles sortent de propose : à partir de number, c'est le même graphe, le même rapport, la même relecture et la même pull request qu'une veille. Une correction de traduction met mode = "translation" et saute la relecture croisée du français.

Aucun test n'appelle la vraie API. vault-watch eval est la mesure sur de vraies veilles (résultats dans metrics/eval/).

Par où commencer la lecture

  1. state.py : ce qu'un passage sait à chaque étape.
  2. graph.py, build() : les étapes et les arêtes, puis l'étape qui vous intéresse.
  3. llm.py : cache, outils web, journal des coûts, en 120 lignes environ.
  4. vault.py, check() et apply() : pourquoi le modèle ne peut pas abîmer une page.
  5. web.py ou cli.py : comment les passages sont lancés, mis en pause et repris.

Ces pages existent aussi en HTML dans docs/, pour lire une copie téléchargée du dépôt avec les schémas : elles sont générées à partir du Markdown par docs/build_html.py.
